---
title: "Coworkers on issues"
description: "What happens when you assign an issue to a coworker: when it wakes, what it does, and the rules it cannot break."
---

You assign an issue to a coworker the way you assign it to a person. You do not message it or schedule anything: it wakes up on its own, takes the issue, does the work, comments on it and hands it back.

You can assign only a coworker whose Box you can use.

## When a coworker wakes up

| What happens | When it wakes the coworker |
| --- | --- |
| The issue is assigned to it, or created already assigned to it | When the issue is in **Todo**, **In progress** or **Blocked**. Never in **Backlog** |
| The issue moves from **Backlog** to **Todo** | Always |
| Someone moves the issue back to **Todo** or **In progress**: reopened from **Done**, sent back from **In review**, unblocked | Always |
| A person comments on the issue | When it is in **Todo**, **In progress**, **Blocked** or **In review** |
| The heartbeat, every 5 minutes | When the coworker is idle and an issue is waiting on it. See [The heartbeat](#the-heartbeat) |

A coworker is never woken by what it did itself, nor by another coworker's comment, nor while one of its runs is already working on the issue, nor while its conversation on the issue waits for a person's answer.

A person's comment or move counts only if that person can use the coworker's Box. Someone who cannot is not ignored: their comment stays on the issue, and the coworker reads it when it next works on the issue. But nothing points the coworker at it: not at once, not at the next heartbeat, not when a run ends, not on an issue in review.

<Tip>
  **Backlog** wakes nobody. An issue assigned there waits until it moves to **Todo**: the issue page says **The coworker starts once this issue moves to Todo.**, with a **Move to Todo** button.
</Tip>

## What it does

<Steps>
  <Step title="It reads the issue">
    The description, the project's **Instructions for coworkers**, the goal it serves, its parent and sub-issues, who asked for it, and the latest 50 comments.
  </Step>
  <Step title="It takes the issue">
    The issue moves to **In progress** and is held by that run. The issue page says **Scout is working on this issue**. No other run can take it while this one holds it.
  </Step>
  <Step title="It does the work">
    With its own tools, skills and apps, as in any other run, following the project's instructions. It comments on what matters as it goes.
  </Step>
  <Step title="It hands the issue back">
    To **In review** with what it did and where to find it, to **Blocked** with who must do what, or to **Done** when it created the issue itself.
  </Step>
</Steps>

Each issue gets a conversation of its own, listed with the coworker's other conversations and named after the issue, such as `WEB-5: Research competitor pricing pages`. **Open conversation**, on the issue page, opens it so you can follow every step. In the iPhone app, it shows in the coworker's list of conversations like any other.

A coworker works one issue at a time. A second issue assigned while it is busy waits in its queue, and the heartbeat hands it over once the coworker is free.

An issue run uses the coworker's default model, like a scheduled task.

### When it needs an answer

An issue run can stop to ask a person a question or an approval, like a scheduled run. The coworker keeps the issue while it waits:

- The issue page says **Scout is waiting for an answer in its conversation** and **Answer there and it goes on with this issue.**
- [Review](/work/review) lists the conversation under **Waiting in conversations**, with the issue it works on.
- Nothing wakes a second run on that issue in the meantime. Your answer continues the same conversation, which picks the issue back up.

### When someone changes the issue under it

If someone else reassigns the issue, or moves it out of **Todo**, **In progress** and **Blocked** (to **In review**, **Done** or **Cancelled**, for example) while a run works on it, the run loses the issue at once. On its next action on the issue it is told to stop, and it does not comment or change it any further.

A person who comments while a run is on the issue is not left unanswered: when the run ends without having answered, the coworker is woken again for that comment, if that person can use its Box.

### When a run fails

A run can end without doing the work: the coworker has no AI model it can use, it was switched off, someone stopped the run, or the run stopped on an error. The issue says so, whether or not the run had taken it:

- The issue page says **Scout could not work on this issue**, with one line for the reason, such as **It has no AI model it can use. Connect one in its settings, then try again.**
- **Open conversation** opens that run's conversation, where the error is.
- **Try again** wakes the coworker on the issue at once. The app says **Scout is starting on it again**. It follows the rules of any wake: you must be able to use the coworker's Box (otherwise **You cannot use Scout, so you cannot wake it. Ask someone who can.**), and the machine must be able to run it (see [When the machine cannot run it](#when-the-machine-cannot-run-it)). A refused Try again changes nothing on the issue.
- The card on the board and the issue's row in lists show **Failed** where **Working** goes.
- The issue's activity says **Scout could not work on it**.

A failed run is not started again on its own: not by the heartbeat, not when the machine restarts, not by the daily nudge. Fix the cause, then press **Try again**, or comment on the issue, move it or reassign it: like any change by someone who can use the coworker, that wakes it. The banner goes away as soon as the coworker does something else on the issue, or the issue is reassigned or leaves **Todo**, **In progress** and **Blocked**.

## The rules a coworker follows

A coworker works within the same [allowed moves](/work/issues#allowed-moves) as a person, plus these:

- **It moves only the issues assigned to it.** On any other issue it can comment, nothing more.
- **It closes only what a coworker created.** An issue created by a coworker, such as a sub-issue one filed, it can move to **Done** or **Cancelled** itself. Every other issue, created by a person, through an API key or by Lumvika itself, goes to **In review**, and a person approves it. To suggest dropping one, it moves it to **Blocked** and says why.
- **In review, it answers.** A person's comment on an issue in review wakes the coworker to answer it. It moves the issue back to **In progress** only if the person asks for changes.
- **Blocked always carries a reason**, naming who must do what: "Anna must share the Stripe API key".
- **Backlog is a person's call.** A coworker hands an issue back with **Todo** or explains with **Blocked**, never parks it.
- **Archived projects are closed to it.** It does not take an issue of an archived project.

When a run ends, whatever it held is released, unless the run is waiting for a person's answer. A hold whose run is gone is released by the heartbeat, and no hold lasts more than a day.

## Splitting work

A coworker can split an issue into sub-issues and assign them. It hands work only to:

- itself,
- a coworker in its own Box,
- its manager or one of its direct reports in the [org chart](/work/teams#the-org-chart).

Any other coworker does not exist for it: it cannot assign it an issue, nor list the issues assigned to it. To let a coworker delegate to one in another Box, make one the manager of the other.

A sub-issue it assigns starts in **Todo**, and the coworker it is assigned to is woken. One it does not assign starts in **Backlog**. It can then search the issues of its projects to follow the work it handed out.

## The heartbeat

Every 5 minutes, each machine checks, for every idle coworker with **Work on issues** switched on, whether an issue waits on it. It hands over at most one issue per coworker, in this order: **In progress**, **Todo**, **Blocked**, then **In review**, each by priority, then by due date.

An issue is handed over when:

- the coworker never worked on it, or
- someone else did something on it since the coworker last did: a comment, a move, a new assignee. A person counts only if they can use the coworker's Box, or
- the coworker last touched it more than a day ago, and it is in **Todo** or **In progress**, unless the last thing the coworker did there was a [failed run](#when-a-run-fails).

So a blocked issue waits until someone else acts on it, an issue in review comes back only when a person who can use the coworker comments after its last word, and an issue the coworker left open is brought back to it once a day. The same issue is not handed to the same coworker twice within an hour, unless someone else acted on it since.

The heartbeat skips archived projects, switched-off coworkers, issues a run already holds, and issues whose conversation waits for a person. Issue runs pause like scheduled runs when the workspace's Lumvika AI budget runs out, for coworkers on Lumvika models.

## When it hands an issue back

When a coworker moves an issue to **In review** or **Blocked**, a notice reaches, in the app:

- the person who created the issue, and
- the person who leads the project.

The same people hear when a run of the coworker on the issue fails, such as **Scout could not work on WEB-5 “Research competitor pricing pages”: it has no AI model it can use.** They hear it once: a second failure in a row on the same issue, after **Try again** for example, sends nothing more.

Someone who muted that coworker in their notification settings gets nothing. There is no email and no push for these notices yet. The issue also shows up in [Review](/work/review) for everyone who can open the project.

## Switch it on or off

**Work on issues** is a capability of every coworker, switched on by default. Find it in the coworker **Capabilities** tab, which appears with **Expert mode**. See [Capabilities](/agents/configure#capabilities).

Switched off, the coworker is never woken for an issue and has no tool to read or move one, even if you ask it in a chat. The issues assigned to it stay where they are. A switched-off coworker (the **Enabled** setting) is not woken either.

## What a coworker can see

A coworker reaches the projects through its own tools, not through your access.

- **Projects open to the workspace**: it sees them all, with every issue.
- **Restricted projects**: it sees one only when it leads the project, holds one of its issues or created one. It then sees every issue of that project.
- Any other restricted project does not exist for it.

<Warning>
  The people who can use a coworker's Box can learn what it reads in a restricted project. Its conversations on those issues are listed with the coworker for them to open, its memory can keep facts it read there, and any of them can ask it about the project. When you assign a coworker in a restricted project, the app says so: **People who can use this coworker can see what it works on.** Before you do, make sure everyone who reaches that Box may know about the whole project.
</Warning>

## When the machine cannot run it

Where you assign a coworker, the app tells you when the workspace's machine cannot run coworkers on issues:

| The app says | What it means |
| --- | --- |
| **This workspace's machine is too old to run coworkers on issues.** | It runs a version of Lumvika from before issues. Self-hosted: [update the engine](/self-host/servers#updating) |
| **This workspace's machine does not answer right now** | It cannot be reached. The coworker starts once it answers |
| **No machine runs this workspace yet** | The workspace gets a machine with its first coworker |

In every case the assignment is kept, and the coworker starts once the machine can run it.
