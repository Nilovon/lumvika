Bug reports, fixes and docs are welcome. This page is the short version of `CONTRIBUTING.md` at the root of the repository.

## Run it from source

You need Node 22, pnpm 8 (`corepack enable`), Docker for the local stack, and an OpenRouter key.

<Steps>
  <Step title="Install and start the local stack">
    ```bash
    pnpm install
    pnpm db:start           # Postgres, Mailpit and an S3 store, migrated, with the services catalog
    ```
  </Step>
  <Step title="Configure the app">
    ```bash
    cp .env.example .env
    ```

    In `.env`, set `NEXT_PUBLIC_APP_URL=http://localhost:3050`, `OPENROUTER_API_KEY`, and the local stack:

    ```bash .env
    DATABASE_URL=postgres://lumvika:lumvika@127.0.0.1:54432/lumvika
    S3_ENDPOINT=http://127.0.0.1:54437
    NEXT_PUBLIC_STORAGE_URL=http://127.0.0.1:54437
    S3_ACCESS_KEY_ID=lumvika
    S3_SECRET_ACCESS_KEY=lumvika-secret
    SMTP_URL=smtp://127.0.0.1:54435
    ```

    Then generate the secrets and hand the file to the app:

    ```bash
    node scripts/self-host-check.mjs
    cp .env apps/ui/.env
    echo "LUMVIKA_ENGINE_URL=http://localhost:3000" >> apps/ui/.env
    ```

    `LUMVIKA_ENGINE_URL` gives the engine below to the first workspace that needs one.
  </Step>
  <Step title="Start the app">
    ```bash
    pnpm --filter @lumvika/contracts build
    pnpm dev:ui             # http://localhost:3050
    ```
  </Step>
  <Step title="Start the engine">
    In another terminal:

    ```bash
    cp apps/engine/.env.example apps/engine/.env
    ```

    In `apps/engine/.env`, set `LUMVIKA_API_KEY` to the `LUMVIKA_ENGINE_API_KEY` of `.env`, and `LUMVIKA_HUB_BASE_URL=http://localhost:3050`. Then:

    ```bash
    pnpm dev:engine         # http://localhost:3000
    ```
  </Step>
</Steps>

Sign-in codes land in Mailpit, at [http://localhost:54436](http://localhost:54436).

To work on these docs, run `pnpm dev:docs` and open [http://localhost:3333](http://localhost:3333).

## Checks

```bash
pnpm -r --if-present ts-check
pnpm --filter lumvika lint
pnpm --filter lumvika test
pnpm --filter lumvika-engine test
pnpm --filter @lumvika/db test
```

CI runs the same, plus every migration and the catalog on an empty database and a build of both Docker images.

## The code

| Path | What it is |
|---|---|
| `apps/ui` | The web app and its API (Next.js). Talks to Postgres, the file store and the engine of each workspace |
| `apps/engine` | The engine: runs the coworkers, their tools, their memory, their browser and screen |
| `apps/docs` | This documentation (Mintlify) |
| `packages/contracts` | Types and schemas shared by the app and the engine |
| `packages/ui` | The design system and the board |
| `packages/db` | The database: schema, migrations, query helpers and row level security tests |

`CLAUDE.md` holds the conventions of the codebase, and is what coding agents read. Three of them matter most:

- **Database access** goes through the typed helpers of `@lumvika/db`, for reads and for writes, with the scope of the caller so row level security applies.
- **Responsive** from the first version: every screen works on a phone, a tablet and a desktop.
- **Engine data-dir migrations**: anything that changes what the engine keeps on disk is a new numbered step at the end of its ladder, never an edit of a shipped one. Details in `apps/engine/README.md`.

A schema change starts in `packages/db/src/schema`: `pnpm db:generate` writes its migration, and `pnpm db:reset` replays every migration and the catalog on the local stack.

`apps/ui/cloud/` is the seam where Lumvika Cloud plugs in billing, paid apps, emails and its machine pool. In this repository it holds the self-hosted behaviour. Pull requests that change what it exports are unlikely to be merged.

## Pull requests

1. Open an issue first for anything bigger than a fix, so you agree on the direction before writing code.
2. Keep a pull request to one change, with tests where the code has them.
3. Sign the CLA when the bot asks: once, for all your contributions.

Lumvika is developed in a private repository that Lumvika Cloud deploys from, and this repository is published from it at each release. A merged pull request is applied there with its author kept, and comes back here with the next release, credited in the release notes.

What will not be merged: anything that touches `apps/ui/cloud/`, a dependency with a license incompatible with the AGPL, or a feature that only makes sense for one deployment.
