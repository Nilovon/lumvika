Start with the logs. Most problems say their cause there in one line.

```bash
docker compose logs --since 30m migrate app engine
```

## The app does not start

`docker compose ps -a` shows `migrate` exited with an error, and `app` never started: the app waits for the migrations. Read why:

```bash
docker compose logs migrate
```

- **`password authentication failed`**: `POSTGRES_PASSWORD` changed after the first start. Postgres keeps the password it was created with: put the first one back in `.env`.
- **`did not create the buckets`**: the file store refused `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY`, or `S3_ENDPOINT` points at a store that does not answer. The store docker compose runs keeps the keys it was first started with, like Postgres.
- **`extension "vector" is not available`**: your own `DATABASE_URL` points at a Postgres without pgvector. Install it there, or leave `DATABASE_URL` empty.

After fixing `.env`, run `docker compose up -d` again: `migrate` runs on every start and only applies what is missing.

## "We could not send your code. Try again."

The app could not hand the email to a mailer. The app logs say why, on a line starting with `[auth]` or `[email]`:

```bash
docker compose logs app | grep -E '\[(auth|email)\]'
```

- **`RESEND_API_KEY missing`**: neither `RESEND_API_KEY` nor `SMTP_URL` reached the app. docker compose points `SMTP_URL` at its mail catcher by default: check `.env` does not set it to an empty value on purpose, then `docker compose up -d`.
- **A Resend error**: the key is wrong, or `RESEND_FROM` is not on a domain verified in Resend.
- **An SMTP error**: `SMTP_URL` is wrong, or the server refuses `RESEND_FROM` as a sender.

## No sign-in code arrives

0. **The mail catcher.** Without `RESEND_API_KEY` or `SMTP_URL` in `.env`, every code lands in the mail catcher at `http://localhost:3003`, on the machine running docker compose, never in a real inbox. On a server, reach it with `ssh -L 3003:localhost:3003 <server>`, or set up [email](/self-host/install#3-set-up-email).
1. **The sender.** With Resend and no verified domain, `RESEND_FROM` falls back to Resend's test sender, which only delivers to the address of your Resend account. Verify your domain and set `RESEND_FROM` on it.
2. **The logs.** With Resend, its dashboard's **Emails** page shows each email and why it bounced. With SMTP, the app logs show the server's answer.
3. **The spam folder**, with a domain that has no SPF or DKIM records especially.

A code works for 15 minutes, and five wrong tries discard it: ask for a new one.

## "permission denied" from Postgres

The database is missing migrations, or a query ran as the wrong role. `migrate` applies every migration of `packages/db/migrations` that is missing, on every start:

```bash
docker compose up -d
docker compose logs migrate
```

After an update, `docker compose pull` first: a release can add migrations.

## Images and avatars do not load

The browser loads them straight from the file store, at `NEXT_PUBLIC_STORAGE_URL`. Open one image's address in a new tab:

- **It does not answer**: the port (`LUMVIKA_STORAGE_PORT`, 3002 by default) is closed, or the reverse proxy does not forward the storage domain. See [On a server](/self-host/install#on-a-server).
- **`AccessDenied`**: the bucket is not public yet. Run `docker compose up -d`: `migrate` opens the public buckets.
- **The address is wrong**: fix `NEXT_PUBLIC_STORAGE_URL` in `.env`, then `docker compose up -d`.

## The app keeps an old address

The app writes `NEXT_PUBLIC_APP_URL`, `NEXT_PUBLIC_STORAGE_URL`, `NEXT_PUBLIC_OAUTH_PROVIDERS` and `ADMIN_EMAILS` into its pages once, when its container is created. `docker compose up -d` recreates it after a change of `.env`. If the logs say a value `changed since this container started`, force it:

```bash
docker compose up -d --force-recreate app
```

The captcha site keys and `NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN` are the exception: only [your own build](/self-host/install#build-the-images-yourself) bakes them in.

## Your own build fails for lack of memory

Symptoms: `Killed`, exit code `137`, or `JavaScript heap out of memory` while building the app with `docker-compose.build.yml`.

The app build needs about 8 GB of memory. In Docker Desktop, raise it in **Settings > Resources > Memory**. On a small VPS, add swap, build the image on another machine, or use the published images.

## "password authentication failed" for user lumvika

Postgres keeps the password it was created with. The `secrets` volume holds the one generated on the first start: if it was deleted while `postgres-data` was kept, or `POSTGRES_PASSWORD` in `.env` changed, the two no longer match. Put the original password back in `.env` as `POSTGRES_PASSWORD`, then `docker compose up -d`.

## "This workspace has no server yet", or a coworker "could not be built"

The engine docker compose started already belongs to another workspace. It goes to the first workspace that needs an engine, which can be a workspace you created while trying things out.

Either [pair a server](/self-host/servers#add-a-server) for this workspace, or free the compose engine in the database (see [Common tasks](/self-host/administration#common-tasks)) and place a coworker again.

## The app cannot reach your server

The pairing says: "The app cannot reach your server at ...". The app checks the address before attaching the server, from inside its own container.

- **The address.** Is it the one in the message? Without `LUMVIKA_PUBLIC_URL`, the app guesses from where the request came from, which is wrong behind a proxy, a NAT or a tunnel. Set `LUMVIKA_PUBLIC_URL` in the command.
- **The port.** The command publishes the engine on port 3000 with `-p 3000:3000`. Check nothing else holds it.
- **The firewall.** Open port 3000 to the app's machine only, or use HTTPS behind a proxy. See [Networking](/self-host/servers#networking).
- **Tailscale.** Both machines on the same tailnet, and the server's Tailscale IP as the address, not its MagicDNS name.

Run `curl http://<address>/health` from the app's machine: it must answer before the pairing can.

## The server cannot reach the app

The server logs say `pairing not done yet` a few times, then `pairing failed`.

`LUMVIKA_HUB_URL` in the command is your `NEXT_PUBLIC_APP_URL`. When it is `http://localhost:3000`, a server elsewhere cannot reach it, and a container on the same machine reaches itself. Give the app an address the server can reach, run `docker compose up -d`, and click **Add server** again.

## The pairing token expired, or was already used

A token works once, for 15 minutes, for one workspace. Click **Add server** again for a new command, then:

```bash
docker rm -f lumvika-engine
```

and run the new command. The volume keeps its data.

## A coworker answers "Set OPENROUTER_API_KEY to run the Lumvika models"

The coworker is on a Lumvika model, and the app has no OpenRouter key. Either:

- put your key in `OPENROUTER_API_KEY` in `.env` and run `docker compose up -d`, or
- connect another provider in **AI providers** and pick it in the coworker's model picker. See [AI models](/self-host/models).

## A coworker on your own model answers "Could not reach the custom endpoint"

The engine could not reach the server of a **Custom endpoint** connection. The message names the address it tried.

- Check the server is running: `curl http://localhost:11434/v1/models` on its machine should list the models.
- The engine runs in a container: `localhost` there is the container. Use `host.docker.internal` (the Compose file maps it) or the machine's network address.
- Ollama on Linux only listens on `127.0.0.1` by default: start it with `OLLAMA_HOST=0.0.0.0`.

If the model answers but forgets its instructions, its context is too small. See [Your own model](/self-host/models#your-own-model).

## The Steward does not answer

With `OPENROUTER_API_KEY` set, the Steward walks a new workspace through its onboarding on that key: look for `[llm]` or OpenRouter errors in `docker compose logs app`, an empty balance or a spending limit on the key stops it too.

Without the key, the Steward skips the onboarding and runs on the AI you connect. If it answers "Set OPENROUTER_API_KEY to run the Lumvika models", connect a provider or your Claude or ChatGPT plan from its model picker and pick it.

## A Composio app does not connect

**"Composio connections are not configured on this server"**: add the API key under **Composio** in the workspace menu, or set `COMPOSIO_API_KEY` in `.env` and run `docker compose up -d`.

**"… needs a Composio auth config"** or **an error from Composio when you click Connect**: the app has no auth config of yours yet. The ids shipped in the catalog are empty. Pick or create one under **Composio** in the workspace menu. See [Composio](/self-host/services#composio).

## The screen does not show

The browser opens a coworker's screen directly on the server's address, over `ws://` or `wss://`.

- **The engine started by docker compose** needs `LUMVIKA_ENGINE_BROWSER_URL`: its `https` domain on a server, as in [On a server](/self-host/install#on-a-server).
- **Your browser must reach the server.** On Tailscale, the person watching must be on the tailnet too.
- **HTTPS on both sides.** When the app is on `https://`, the server must be too, or the browser blocks the connection. Put it behind [Caddy](/self-host/servers#networking).
- **The screen was turned off** with `LUMVIKA_DESKTOP=off` on the server.

## Web search does not work

Coworkers search the web through Brave. Set `BRAVE_SEARCH_API_KEY` and run `docker compose up -d`.

## An engine misbehaves after an update

Check its data-dir. The command changes nothing:

```bash
docker compose exec engine node dist/cli/bin.js doctor
```

`/health` also reports `dataVersion` against `dataVersionTarget`. An engine older than its data-dir leaves the data untouched and boots: update the engine image rather than restoring an older archive.

## Chat says to update the server

**Update your machine to use Chat** means the workspace's engine predates Chat. Update it: see [Updating](/self-host/servers#updating). **Chat needs a machine** means the workspace has none yet: add a coworker, or [add a server](/self-host/servers).

## A coworker does not pick up its issues or react to a comment

Check, in this order:

- **Its last run failed.** The issue page says **Scout could not work on this issue**, with the reason, and the card shows **Failed**. A failed run is never started again on its own, after an engine restart included. On a fresh install the reason is usually **It has no AI model it can use. Connect one in its settings, then try again.**: put a key in `OPENROUTER_API_KEY` or connect a provider, see [AI models](/self-host/models). Fix the cause, then press **Try again** on the issue, or open the run's conversation with **Open conversation** to read the error.
- **The issue is in Backlog.** A coworker is not woken for a backlog issue. Move it to **Todo**.
- **Work on issues is off** in the coworker **Capabilities** tab, or the coworker is switched off.
- **The engine predates issues.** The issue page says **This workspace's machine is too old to run coworkers on issues.** where you assign the coworker, and the app logs `this engine cannot start issue runs yet` once per engine. Update it.
- **The coworker is waiting for an answer** in its conversation on the issue. The issue page says so: answer there.
- **You cannot use the coworker's Box.** Your comment or move is saved but never wakes the coworker, at once or later. It reads your comment the next time it works on the issue. Ask someone who can use it to comment.
- **The coworker is busy.** It works one issue at a time. The next one waits for the heartbeat, every 5 minutes, once the coworker is idle.
- **The engine cannot reach the app** at `LUMVIKA_HUB_BASE_URL`: the coworker can neither read the issue nor ask for the next one. Look for `work queue call failed` or `work queue sweep failed` in `docker compose logs engine`.

See [Coworkers on issues](/work/coworkers-on-issues) for every rule that decides when a coworker wakes.

## A coworker does not answer in a channel

The thread says why, under the message. The table in [When a coworker cannot answer](/work/channels#when-a-coworker-cannot-answer) lists every reason. **needs an update** means the engine predates Channels: update it.

## Still stuck

Open an issue on [GitHub](https://github.com/nilovon/lumvika/issues) with what you ran, what you expected, and the output of `docker compose logs --since 30m app engine`. Remove keys and tokens first.
