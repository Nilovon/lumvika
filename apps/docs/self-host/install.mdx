Lumvika ships as two public images on GitHub, `ghcr.io/schnebel-technologie/lumvika-app` and `ghcr.io/schnebel-technologie/lumvika-engine`. One `docker-compose.yml` runs them with everything they need next to them: Postgres, an S3 file store, a mail catcher, and the secrets, generated on the first start. Nothing to build, nothing to clone.

## Before you start

- **Docker** with Docker Compose 2.24 or newer. Give Docker at least 4 GB of memory and 15 GB of disk.
- **On a server:** a domain for the app, one for the engine, one for the file store, a reverse proxy for HTTPS, and a way to send email. See [On a server](#on-a-server).
- **Optional, an OpenRouter key** from [openrouter.ai/keys](https://openrouter.ai/keys). It runs the Steward's onboarding and the default models of every coworker. Without it, connect your own AI in the app, your Claude or ChatGPT plan included.

## 1. Start Lumvika

```bash
mkdir lumvika && cd lumvika
curl -fsSLO https://raw.githubusercontent.com/schnebel-technologie/lumvika/main/docker-compose.yml
docker compose up -d
```

The first start pulls the images, a few minutes on a slow connection. Then, every time:

1. `secrets` generates the passwords and keys of this install, once, into the `secrets` volume.
2. `postgres`, `storage` and `mailpit` start.
3. `migrate` applies the database migrations, creates the storage buckets and loads the services catalog into an empty database.
4. `app` and `engine` start.

Open [http://localhost:3000](http://localhost:3000). That is the whole install on your own computer.

## 2. Sign in

You land on the board with a sign-in dialog on top. Enter your email: a 6-digit code is sent to it.

Until you [set up email](#3-set-up-email), every email the app sends lands in the mail catcher at [http://localhost:3003](http://localhost:3003), on this machine only. Open it, copy the code, type it in.

There is no phone sign-in, and no Google or Apple button unless you [configure them](/self-host/configuration#sign-in).

## 3. Set up email

The mail catcher is enough to try Lumvika alone. For anyone else to sign in, Lumvika needs a real way to send email. Create a `.env` next to `docker-compose.yml`, with one of the two:

<Tabs>
  <Tab title="Resend (recommended)">
    1. Create an account on [resend.com](https://resend.com), add your domain in **Domains** and publish the DNS records it lists.
    2. Create a key in **API Keys**.

    ```bash .env
    RESEND_API_KEY=re_...
    RESEND_FROM=Lumvika <lumvika@example.com>
    ```

    `RESEND_FROM` is an address on the domain you verified. Until the domain is verified, Resend only delivers to the address of your Resend account.
  </Tab>
  <Tab title="Your own SMTP server">
    Any mailbox provider that gives SMTP credentials works. `smtps://` for port 465, `smtp://` for 587 or 25:

    ```bash .env
    SMTP_URL=smtps://<user>:<password>@smtp.example.com:465
    RESEND_FROM=Lumvika <lumvika@example.com>
    ```

    `RESEND_FROM` is the sender of every email, whatever sends it: use an address your SMTP server accepts.
  </Tab>
</Tabs>

Then `docker compose up -d` again. The sign-in email is built by the app, in the language of the account: there is no template to paste anywhere.

## 4. The rest of `.env`

Every value is optional. The ones you will want first:

```bash .env
OPENROUTER_API_KEY=sk-or-...
ADMIN_EMAILS=you@example.com
```

[`.env.example`](https://github.com/schnebel-technologie/lumvika/blob/main/.env.example) lists every variable with a comment, and [Configuration](/self-host/configuration) explains each one. After any change, `docker compose up -d` recreates the containers that read it.

The passwords and keys of this install live in the `secrets` volume. A value you put in `.env` wins over the generated one. To keep them in `.env` instead, for a backup or to move the install, print them once:

```bash
docker compose run --rm --entrypoint cat secrets /run/lumvika/generated.env
```

and copy each value into `.env` under its name without the `GENERATED_` prefix.

## 5. Check it runs

```bash
docker compose ps -a                                            # postgres, storage, mailpit, app and engine are "running", secrets and migrate "exited (0)"
curl -s http://localhost:3000/api/version                       # the app answers
docker compose exec engine curl -s http://localhost:3000/health # the engine answers
docker compose exec engine node dist/cli/bin.js doctor          # the engine data-dir is healthy
```

When something is off, read the logs first:

```bash
docker compose logs -f migrate app engine
```

## On a server

On your own computer, skip this section. On a server, people reach Lumvika over HTTPS and nothing else stays open.

Set the public addresses and a way to send email (see [step 3](#3-set-up-email)) in `.env`:

```bash .env
NEXT_PUBLIC_APP_URL=https://lumvika.example.com
LUMVIKA_ENGINE_BROWSER_URL=https://engine.example.com
NEXT_PUBLIC_STORAGE_URL=https://files.example.com
RESEND_API_KEY=re_...
RESEND_FROM=Lumvika <lumvika@example.com>
```

The app writes these addresses into its pages when it starts: `docker compose up -d` applies them, no build needed.

The engine and the file store need their own domains: a browser connects to the engine directly to show a coworker's screen, and loads avatars, logos and images straight from the file store. Point the domains at the server, then put a reverse proxy in front. With [Caddy](https://caddyserver.com), which gets its certificates on its own and forwards WebSockets:

```text Caddyfile
lumvika.example.com {
    reverse_proxy localhost:3000
}

engine.example.com {
    reverse_proxy localhost:3001
}

files.example.com {
    reverse_proxy localhost:3002
}
```

<Warning>
  docker compose publishes the app on port 3000, the engine on port 3001 and the file store on port 3002. Docker opens these ports past `ufw`, so they end up on the internet without the reverse proxy in front. Close them in your provider's firewall, and keep only 22, 80 and 443 open. Postgres is not published at all, and the mail catcher only on `127.0.0.1`: whoever reads it can sign in as anyone, so never publish it.
</Warning>

Without a firewall at your provider, this `nftables` rule does the same. Replace `eth0` with your network interface:

```text /etc/nftables.conf
table inet lumvika_edge {
  chain prerouting {
    type filter hook prerouting priority -300; policy accept;
    iifname "eth0" tcp dport { 3000, 3001, 3002 } drop
  }
}
```

Then `nft -f /etc/nftables.conf` and `systemctl enable nftables`.

## Meet your first coworker

The emails in `ADMIN_EMAILS` see the admin switches in the app. See [Administration](/self-host/administration).

The Steward, Lumvika's guide, greets you and asks what you need done. Answer in plain words: it plans a team and builds it. You can also click the board to create a coworker yourself and describe its job in the chat.

The first coworker you place on the board needs a machine to run on. Your first workspace takes the engine that docker compose started, with nothing to configure. The second workspace, and every one after it, needs a [server of its own](/self-host/servers).

From here, the coworker works exactly as on Lumvika Cloud: see the [Quickstart](/quickstart) from step 4.

## Updating

```bash
docker compose pull
docker compose up -d
```

`latest` follows every release. To stay on a version, set `LUMVIKA_VERSION=0.5` in `.env` (the patches of 0.5) or `LUMVIKA_VERSION=0.5.1` (exactly that one). Fetch `docker-compose.yml` again when a release's notes say so.

The engine migrates its data-dir on start, and the `migrate` step applies the database migrations a release adds before the app starts. Back up first: see [Backups](/self-host/servers#backups).

## Build the images yourself

For modified code, or for the browser keys only a build bakes in (the captcha site keys and `NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN`), build both images from a clone. It needs 6 GB of memory for Docker and about 40 GB of disk.

```bash
git clone https://github.com/schnebel-technologie/lumvika.git && cd lumvika
cp .env.example .env
docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build
```

When you run modified code for others, set `NEXT_PUBLIC_SOURCE_REPO_URL` to the repository holding it: the AGPL asks you to offer its source.
