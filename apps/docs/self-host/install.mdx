This page takes about ten minutes, plus the time Docker needs to build the two images the first time.

## Before you start

- **Docker** with Docker Compose. Give Docker at least 6 GB of memory: the app build needs it, and 60 GB of disk: the images and the build cache take about 40.
- **Node.js 22**, for the setup check.
- **Git**.
- **On a server:** a domain for the app, one for the engine, one for the file store, and a reverse proxy for HTTPS. See [On a server](#on-a-server).
- **A way to send email**: a [Resend](https://resend.com) account or any SMTP server. People sign in with a code sent by email.
- **An OpenRouter key** from [openrouter.ai/keys](https://openrouter.ai/keys). It runs the Steward's onboarding and the default models of every coworker. Without it, connect your own AI in the app, your Claude or ChatGPT plan included.

## 1. Get the code

```bash
git clone https://github.com/schnebel-technologie/lumvika.git && cd lumvika
cp .env.example .env
```

Every command below runs from this folder.

## 2. Set up email

The database and the file store need nothing from you: docker compose runs Postgres and an S3 store next to the app, and creates what they need on the first start. Email is the one thing to set up: people sign in with a 6-digit code sent by email, and without a mailer nobody can sign in.

<Tabs>
  <Tab title="Resend (recommended)">
    1. Create an account on [resend.com](https://resend.com), add your domain in **Domains** and publish the DNS records it lists.
    2. Create a key in **API Keys**.

    ```bash .env
    RESEND_API_KEY=re_...
    RESEND_FROM=Lumvika <lumvika@example.com>
    ```

    `RESEND_FROM` is an address on the domain you verified. Until the domain is verified, Resend only delivers to the address of your Resend account: enough to sign in yourself, not for a team.
  </Tab>
  <Tab title="Your own SMTP server">
    Any mailbox provider that gives SMTP credentials works. `smtps://` for port 465, `smtp://` for 587 or 25:

    ```bash .env
    SMTP_URL=smtps://<user>:<password>@smtp.example.com:465
    RESEND_FROM=Lumvika <lumvika@example.com>
    ```

    Keep `RESEND_API_KEY` empty: the app sends through `SMTP_URL` only when it is. `RESEND_FROM` is the sender of every email, whatever sends it: use an address your SMTP server accepts.
  </Tab>
</Tabs>

The sign-in email is built by the app, in the language of the account: there is no template to paste anywhere.

## 3. Fill the rest of `.env`

Three more lines:

```bash .env
NEXT_PUBLIC_APP_URL=http://localhost:3000
OPENROUTER_API_KEY=sk-or-...
ADMIN_EMAILS=you@example.com
```

`NEXT_PUBLIC_APP_URL` is the address people type in their browser, without a trailing slash. Keep `http://localhost:3000` to try Lumvika on this machine. For a team, use the address they will reach it at, for example `https://lumvika.example.com`. `ADMIN_EMAILS` is baked in by the build, so set it now. Every other variable is optional: see [Configuration](/self-host/configuration).

## 4. Run the check

```bash
node scripts/self-host-check.mjs
```

It generates the secrets left empty (the Postgres password `POSTGRES_PASSWORD`, the session secret `BETTER_AUTH_SECRET`, the storage key `S3_SECRET_ACCESS_KEY`, the engine key `LUMVIKA_ENGINE_API_KEY` and the signing secrets), then checks the required values and that one way of sending email is set. It stops with a plain message on anything only you can fix, warns when `OPENROUTER_API_KEY` is empty, and prints the command to start.

## 5. Start Lumvika

```bash
docker compose up -d --build
```

The first build takes several minutes. Later starts take seconds. Every start runs a `migrate` step before the app: it applies the database migrations, creates the storage buckets and loads the services catalog into an empty database.

## 6. Check it runs

```bash
docker compose ps -a                                           # postgres, storage, app and engine are "running", migrate "exited (0)"
curl -s http://localhost:3000/api/version                      # the app answers
docker compose exec engine curl -s http://localhost:3000/health # the engine answers
docker compose exec engine node dist/cli/bin.js doctor         # the engine data-dir is healthy
```

When something is off, read the logs first:

```bash
docker compose logs -f migrate app engine
```

## On a server

On your own computer, skip this section. On a server, people reach Lumvika over HTTPS and nothing else stays open.

Set the public addresses in `.env`, before the build:

```bash .env
NEXT_PUBLIC_APP_URL=https://lumvika.example.com
LUMVIKA_ENGINE_BROWSER_URL=https://engine.example.com
NEXT_PUBLIC_STORAGE_URL=https://files.example.com
```

The engine and the file store need their own domains: a browser connects to the engine directly to show a coworker's screen, and loads avatars, logos and images straight from the file store. Point the domains at the server, then put a reverse proxy in front. With [Caddy](https://caddyserver.com), which gets its certificates on its own and forwards WebSockets:

```text Caddyfile
lumvika.example.com {
    reverse_proxy localhost:3000
}

engine.example.com {
    reverse_proxy localhost:3001
}

files.example.com {
    reverse_proxy localhost:3002
}
```

<Warning>
  docker compose publishes the app on port 3000, the engine on port 3001 and the file store on port 3002. Docker opens these ports past `ufw`, so they end up on the internet without the reverse proxy in front. Close them in your provider's firewall, and keep only 22, 80 and 443 open. Postgres is not published at all: only the containers reach it.
</Warning>

Without a firewall at your provider, this `nftables` rule does the same. Replace `eth0` with your network interface:

```text /etc/nftables.conf
table inet lumvika_edge {
  chain prerouting {
    type filter hook prerouting priority -300; policy accept;
    iifname "eth0" tcp dport { 3000, 3001, 3002 } drop
  }
}
```

Then `nft -f /etc/nftables.conf` and `systemctl enable nftables`.

## 7. Sign in

Open [http://localhost:3000](http://localhost:3000), or your `NEXT_PUBLIC_APP_URL`. You land on the board with a sign-in dialog on top.

Enter your email. A 6-digit code arrives in your inbox, and you type it in. There is no phone sign-in, and no Google or Apple button unless you [configure them](/self-host/configuration#sign-in).

The emails in `ADMIN_EMAILS` see the admin switches in the app. See [Administration](/self-host/administration).

## 8. Meet your first coworker

The Steward, Lumvika's guide, greets you and asks what you need done. Answer in plain words: it plans a team and builds it. You can also click the board to create a coworker yourself and describe its job in the chat.

The first coworker you place on the board needs a machine to run on. Your first workspace takes the engine that docker compose started, with nothing to configure. The second workspace, and every one after it, needs a [server of its own](/self-host/servers).

From here, the coworker works exactly as on Lumvika Cloud: see the [Quickstart](/quickstart) from step 4.

## Updating

```bash
git pull
docker compose up -d --build
```

The engine migrates its data-dir on start, and the `migrate` step applies the database migrations a release adds before the app starts. Back up the database before you update: see [Backups](/self-host/servers#backups).

<Note>
  The values starting with `NEXT_PUBLIC_` are baked into the app when it is built. So is `ADMIN_EMAILS`. After changing one, rebuild with `docker compose up -d --build`. Other values only need `docker compose up -d`.
</Note>
