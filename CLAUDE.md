# Code style

## Comments

Write self-explanatory code instead of comments. Names of variables, functions, and types should make intent clear without explanation.

Do not add comments in most cases. Only add a comment when it genuinely helps: clarifying an ambiguous type, documenting a non-obvious reason for doing something, or explaining a subtle edge case that the code alone cannot convey.

Never add comments that just restate what the code does.

# Skills

Every file under `.claude/skills/` is written in English: the frontmatter, the body, the references,
the comments and the messages printed by the scripts. The repository is international, so a new
skill is born in English even when it is designed in a French conversation.

- The conversation itself follows the user: a skill says "reply in the user's language", never
  "reply in French".
- French stays only where it is a real value: quoted trigger phrases in the `description` (next to
  their English equivalent), Notion statuses and property names, labels of the French `/admin`
  back-office as they appear on screen.

# Responsive

Every design and every UI implementation is responsive from the first version, never as a follow-up. Before calling a screen, dialog, panel or landing section done, check it at mobile (~375px), tablet (~768px) and desktop widths, and on a short viewport (~700px tall):

- nothing overflows horizontally, nothing is cut off, long text wraps or truncates on purpose
- multi-column layouts (dialogs with an illustration column, grids, side panels) stack or drop the secondary column on small screens
- fixed heights and fixed widths give way to `max-h` / `max-w` with scroll inside the content, the header and footer stay reachable
- footers and button rows wrap or stack instead of squeezing
- touch targets stay usable, hover-only affordances have a visible fallback

When a design is proposed (mockup, preview, screenshot), it shows the small-screen version too.

# Verify in the app before calling it done

Lumvika has paying customers: a change that shows anywhere (a screen, a dialog, a button, a flow, an
API route the UI calls, the mobile app) is not done until it has been seen working in the running
app. Tests and the typecheck are not enough. Follow the `verify-in-app` skill without being asked:

- run it on the local stack only (`pnpm db:start`; `pnpm cloud env:local` on Lumvika Cloud), never on production
- `pnpm verify:ui` signs in, captures every width in both themes and reports console errors,
  failed requests and load timings; a scenario in `.context/verify/` clicks the path that changed
- look at every capture, fix what the change broke, run it again
- the final message shows the captures, what was clicked, the errors found, and says plainly what
  could not be tested

# i18n

Lumvika ships language packs (`packages/i18n`, see its README). The source is English; German is
generated by `pnpm i18n:translate` and committed.

- A string a person sees goes through `t()` from next-intl, never written inline in JSX, a toast or a
  zod message: `useTranslations('<namespace>')` in a client component, `getTranslations` on the server.
- One sentence is one ICU key, with its variables and plurals inside: never concatenate translated
  pieces.
- Dates, numbers, sizes and durations go through `@lumvika/i18n/format` with the current locale
  (`useLocale()` in apps/ui, `useUiLocale()` in packages/ui), never `toLocaleString('en-US')`.
- Content stored in the database (templates, services, experts, blog, changelog) stays in English. The
  `/admin` back office stays in French.
- Before the pull request: `pnpm i18n:translate`, then `pnpm i18n:check`. Follow the `i18n-strings`
  skill.

# Database

Postgres, reached through Drizzle (`packages/db`). Who a query runs as is a `DbScope`, the first
argument of every helper: `getRequestScope()` (from `@/lib/auth/session/request`) runs under row level
security as the signed-in user, `userScope(userId)` as a given user, `anonScope()` as a visitor, and
`serviceScope()` bypasses row level security, for server code that has checked access itself.
`inTransaction(scope, async tx => ...)` makes several statements land together.

`apps/ui` imports everything from `@/lib/db`, `cloud/apps/landing` from `@lumvika/db`. Operators (`sql`,
`eq`, `and`, `inArray`, ...) come from there too, never from `drizzle-orm`.

There is no database client in the browser: a client component reads and writes through a server
action that runs on `getRequestScope()` and validates its arguments. Files go through
`@lumvika/storage` (S3), live updates through `@/lib/live` (Postgres LISTEN/NOTIFY over SSE).

## Reads go through the typed helpers

`selectSingle`, `selectMaybeSingle`, `selectFirst`, `selectMany`, `selectAll`, `selectCount` and the
`*WithJoins` variants, all answering `{ data, error }`. Filters are objects: `{ id }`,
`{ status: 'published' }`, `{ id: { neq: current } }`, `{ slug: ids }` (array = IN),
`{ name: { ilike } }`, `{ deleted_at: { isNull: true } }`, `{ or: { a, b } }`. A join config needs
`as const` on the whole object, not just `columns`. No `select('*')`: extract a
`XXX_COLUMNS = [...] as const` list instead.

## Writes go through the write helpers

`insertRows`, `insertRow` (one row, returned), `updateRows`, `deleteRows`, `upsertRows`, each typed by
its table, so the payload needs no annotation:

```ts
await updateRows(scope, 'agents', { name }, { id })
await insertRow(scope, 'agents', { workspace_id, name }, ['id'])
await upsertRows(serviceScope(), 'experts', row, { onConflict: ['slug'] })
```

`updateRows` and `deleteRows` require filters. A spread payload (`{ ...row }`) escapes excess-property
checking, so pin the type where the object literal is built.

## Anything else

SQL functions: `callScalar`, `callRows`, `callColumn`. Any other query: ``queryRows(scope, sql`...`)``
(int8 as numbers, timestamps in ISO 8601), or Drizzle itself through `scope.run(db => ...)` with the
tables of `@lumvika/db/schema`. Error codes: `23505` unique violation, `42501` refused by row level
security or a grant, `NOT_ONE_ROW` from `selectSingle`.

## Schema changes

- The schema lives in `packages/db/src/schema`. Change it there, then `pnpm db:generate` writes the
  migration into `packages/db/migrations`; `pnpm db:start` (or `pnpm db:reset`) applies it locally.
- Policies, grants, functions and triggers go in a custom SQL migration
  (`pnpm --filter @lumvika/db exec drizzle-kit generate --custom --name <what>`).
- Every new public table enables row level security and gets its policies in the same migration:
  `packages/db/src/rls.test.ts` fails on a public table without it.
- A shipped migration is never edited: a fix is a new migration.
- Policies are tested in `packages/db/src` (`pnpm --filter @lumvika/db test`, on the local Postgres),
  like `rls.test.ts` and `space-access.test.ts`.

Before finishing any feature touching the database, grep your own diff for `drizzle-orm` imports and
raw `db.execute` calls that a helper covers.

# Engine data-dir migrations

An engine data-dir can be archived and restored weeks later onto a newer engine. Anything that changes what the engine keeps on disk (a file, a folder, a SQLite schema) is a new numbered step at the end of its ladder: `DATA_DIR_MIGRATIONS` in `apps/engine/src/datadir/migrations.ts`, `SYSTEM_DB_MIGRATIONS` or `SHARED_DB_MIGRATIONS`.

- A shipped step is never edited nor removed, even once every live box has run it.
- A step is re-runnable, and leaves the old engine still running beside it working: add first, remove in a later step.
- A step ships with a test that starts from the previous version.

Details in `apps/engine/README.md`.

# Open source and Lumvika Cloud

This repository is Lumvika, AGPL-3.0. Lumvika Cloud runs the same code with a private `cloud/` folder
cloned inside it (git-ignored here): `@lumvika/cloud/<domain>` resolves to `cloud/packages/cloud/src/<domain>`
when that folder is there, and to `apps/ui/cloud-oss/<domain>` (the behaviour of a self-hosted install)
otherwise. The `paths` fallback of `apps/ui/tsconfig.json` does it for tsc, Next and Trigger.dev, the alias
of `apps/ui/vitest.config.ts` for the tests. A checkout without `cloud/` builds and runs as it is.

- What Lumvika Cloud runs differently (its machine pool, the plans it sells, its support chat) is
  reached only through `@lumvika/cloud/<domain>`. A new symbol there gets its self-hosted twin in
  `apps/ui/cloud-oss/`, with the behaviour of a self-hosted install.
- A test of public code that checks Lumvika Cloud's behaviour pins the `@lumvika/cloud/*` module it reads
  (`vi.mock`), so it passes with and without `cloud/`.

# Commits and pull requests

The repository is public: commit messages, pull request titles and descriptions are written in
English, whatever the language of the conversation.

# Security fixes

Every branch pushed to `origin` is public at once, even without a pull request. A vulnerability fix
never goes there: it starts with `pnpm security:start "<title>"` in a workspace of its own, which opens
a draft GitHub security advisory and its private fork and locks the workspace's push to that fork.
Follow the `security-fix` skill. In that workspace, never use the GitHub MCP write tools: they bypass
git and its lock.
